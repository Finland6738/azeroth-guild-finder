All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Design

- Specification of the first version in `docs/specs/` (SPEC-00 to SPEC-10, in Italian): scope and roles, platform and peer-to-peer architecture, network protocol, data model, interface, applications, emblems, quality and release, risks and open questions.
- Mockups v2 in `docs/specs/mockups/`: design system (Albion-like skin on a Material Design 3 skeleton, Roboto and Roboto Mono), Find a Guild, guild page, listing editor (recruitment and activity steps), emblem designer, applications, notification icon, role-based states. Rendered to WebP by `render.sh`.
- Four roles (Tank, Healer, Melee DPS, Ranged DPS), up to three activities per guild and a commitment level (Casual, Softcore, Hardcore).
- Architecture decisions 0001–0018 in `docs/adr/`.

### Planning

- Development roadmap in `docs/roadmap/`: one file per milestone (M0 spike to M5 release, 44 steps) with branch, dependencies, scope, acceptance criteria, tests, docs and real-client checks, plus the V2 backlog.
- Decisions confirmed by the owner: names (addon, channel `AzGuildFinder`, prefix `AzGF`, `/gf`), one open application per character, optional role checkboxes in the application, 14-day expiry, 7-day cooldown, unique players as a range, anonymous alt count on by default.

- M1.6: `Net/Codec.lua`, the message codec (SPEC-02 §2): `Encode(type, fields)` builds `{v, t, ...}` → CBOR → Deflate when longer than 120 bytes (kept only if smaller) → flag byte (`0x00` raw, `0x01` deflated) → standard Base64; `Decode(payload)` never raises and returns the message or `nil, reason` (`size`, `base64`, `flag`, `inflate`, `cbor`, `shape`, `version`, `type`, `invalid`, `newer`). 8 KB decompressed limit, unknown fields kept, newer `v` sets a one-shot `newerSeen` flag (`ConsumeNewer`). `Codec.SCHEMA` lists the required fields of the 16 message types and `Validate` checks them (deep record validation comes with the Data modules). - M1.7: `Net/Transport.lua`, the send queue between the codec and the wire. `Transport:Send(dist, msg, opts)` (`CHANNEL`, `WHISPER`, `GUILD`, `OFFICER`; `opts` = `target`, `prio`, `key`, `reply`, `ttl`, `onSent`, `onFail`) encodes with the codec, keeps its own queue and hands messages to ChatThrottleLib with the SPEC-02 §4 priorities. NET-01: one CHANNEL message per `CHANNEL_GAP` (1.2 s) and 2 KB per rolling minute, explicit replies (`CATACK`, `DETACK`, ...) excluded from the byte budget; NET-02: one `CAT` and three `DET` per minute; NET-03: nothing is sent during a chat lockdown, an addon restriction (combat, encounter, ...) or while outgoing addon messages are restricted (read-only, `TRANSPORT_READ_ONLY`), only the latest message per `key` is kept, BULK messages older than 10 minutes are dropped; NET-04: a throttle result retries after 4 x the gap, at most 3 times. `InvalidChannel` on CHANNEL switches to **listen-only mode** (`TRANSPORT_LISTEN_ONLY(active, reason)`): queued and new CHANNEL messages are dropped, WHISPER and GUILD go on, one probe message per hour tests the channel again. Receiving: AceComm (prefix `AzGF`) -> `Codec:Decode` -> Bus `NET_MESSAGE(msg, sender, dist)`; invalid or oversized payloads are only counted, a newer protocol raises `PROTOCOL_NEWER` once per session; senders are never printed or stored. Messages over 255 bytes use the AceComm wire format but go to ChatThrottleLib directly, because AceComm's send callback loses the result code (chunks leave room for the prefix until M0 measures the real limit). `/gf debug` gets a Transport section (queued, sent, dropped by reason, throttled, retried, rejected, listen-only reason). `Compat` gained `Now`, `After` and `NewTicker`. `Codec:Encode` now refuses a message above the 8 KB decoded limit instead of sending what every receiver would reject. `Tests/test_transport.lua`. Not yet run against the real throttling and lockdown on Forever (M0 S6 and S11).

- M2.3: `Net/Sync.lua`, the catalog over the hidden channel (SPEC-02 §5–§6). `ANN` and `DEL` from the channel go to the catalog with their sender (INT-04, INT-05); contacts (`c=1`) per guild and the last `ANN` per guild are remembered in memory only (`Sync:Contacts`, `Sync:Suppressed` for the §5 suppression, `Sync:Announce` queues an `ANN`). After `CHANNEL_READY` and a random 5–15 s a client sends `CATREQ` (its digest as flat `h, rev, srev` triples, in parts of 64 listings) unless a full sync finished less than 10 minutes ago (`AzerothGuildFinderDB.syncAt`). Peers elect one responder: answers are scheduled in 0.5–5 s with exponentially spread timers (free peers with more to send first, peers waiting for their NET-02 turn later, "nothing new" acks last and only from a few peers that finished a full sync), the winner's `CATACK{to, nonce, n, w}` cancels the others, and peers that acked at the same moment compare during one second (sooner, then more, then the lowest name hash) so only one sends. The winner whispers `CAT` batches of 10 summaries A→Z with their ANN age, at most one reply per minute (replies are queued and the wait is announced in `w`). Rounds repeat while they bring news; a silent first round is retried after 60 s, three times, then the client relies on the `ANN`. `Sync:RequestDetail(k)` runs the same election for `DETREQ`/`DETACK`/`DET` (three per minute) and emits `DETAIL_UNAVAILABLE(k)` after 20 s; `CATALOG_SYNCED(result)` reports each sync. A listen-only client asks by whisper the last peer it heard and is answered directly. `/gf debug announce` (development builds only: `Config.DEV`, true in a checkout because the packager comments out the `--@debug@` block of `Core/Config.lua`) announces a test listing `AGF Test <character>` with `test = true`, which release builds ignore; summaries gained the optional `test` field (SPEC-03 §2). `/gf debug` gets a Sync section. The Transport gained `opts.rateGroup` so the batches of one `CAT` reply count once for NET-02. The simulator now delivers the messages of each sender–receiver pair in order (multipart AceComm messages were being lost) and takes a `sync` option; single-client tests keep the sync off (`Sync.AUTO`). `Tests/test_sync_sim.lua` measures: 50 clients and 100 guilds converge in 200 simulated seconds with every client inside NET-01 (worst minute 14 channel messages and 2040 of 2048 bytes of requests and announcements, no duplicate `CAT` batch); a late joiner gets 100 listings from exactly one responder in about 15 s; 20 clients and 60 guilds converge in 275 s with 10 % of the messages lost; a listen-only client syncs by whisper; detail fetch and unavailable detail; retries, digest parts and the test listing.
